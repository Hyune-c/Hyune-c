# AI를 적극적으로 활용하는 개발에 대한 생각

> 아직 실무 개발에서는 AI가 만든 코드를 `보지 않고 머지합니다` 수준으로 신뢰하기에는 이르다고 생각합니다.
> - 대신 사람이 반드시 통제해야 하는 영역과 위임 가능한 영역을 분리하면, 직접 보지 않고도 머지할 수 있는 영역은 점진적으로 넓힐 수 있습니다.
> - 이를 위해 스킬과 문서로 구성된 하네스를 만들고 동료와 공유하면서, AI의 불확실성을 제어하고 생산성을 높이는 방식을 선호합니다.
>
> 반대로 사이드 프로젝트와 마이너 개발건에서는 AI 를 적극적으로 활용하여 결과물을 만들고 있습니다.
> - 개인 프로젝트인 [read4ai](https://github.com/read4ai/read4ai-excel) 에서는 결과 중심의 vibe coding 과 harness engineering 을 더 적극적으로
    활용 했습니다.
> - 사용하는 도구도 계속 조정하고 있습니다. 초기에는 `cmux + Claude Code + Codex plugin` 조합을 사용했지만, Opus 4.7 이후 체감되는 수준의 성능 저하가 있어 현재는 Codex
    중심으로 전환했습니다.

## 배경

AI 는 이미 실무 개발에서 필수 불가결적인 존재가 되었습니다.  
하지만 같은 도구를 사용하더라도, 사용하는 사람의 숙련도와 개발 흐름에 따라 결과물의 수준은 크게 달라집니다.

- 랄프 루프를 돌리면 하룻밤 사이에도 결과물이 만들어지지만, 정작 필요한 엣지 케이스나 예외 처리, 운영 중 복구 흐름이 부족한 경우가 많습니다.
- 특히 B2B 에이전트 솔루션의 관점에서는 대량의 지식과 암묵지를 다루기 때문에, 좋은 모델과 프롬프트만으로는 안정적인 결과를 만들기 어렵습니다.

## 통제 영역의 분리

저는 AI 활용에 있어 제일 중요한 점은, 통제해야 하는 영역과 위임 가능한 영역을 분리하는 것이라고 생각합니다.  
실무는 단순히 돌아가는 것만이 아니라 정합성과 지속 가능성이 더 중요하기 때문입니다.

- 통제해야 하는 영역: 도메인 규칙, 비즈니스 흐름, 상태 전이, 인증/과금, 장애 복구, 외부 API spec
- 위임 가능한 영역: 멱등하게 테스트 가능한 컴포넌트, UI 구성, mapper / adapter, 반복적인 boilerplate, 문서 초안

결국 AI와의 개발도 전체를 위임하는 것보다는 분할 정복 방식에 가깝다고 생각합니다.

- 큰 업무를 그대로 AI에게 맡기는 것이 아니라, 개발자가 검토해야 되는 부분과 기계적으로 검증할 수 있는 부분을 나눠야 합니다.
- 그래야 리뷰해야 할 범위를 줄이고, 위임한 부분은 테스트와 계약만으로도 검증할 수 있습니다.

이런 관점으로 개발하다 보니 아키텍처 방법론으로 많이 나오는 Hexagonal Architecture 나 OOP 구조보다, 비즈니스 흐름을 절차적으로 드러내는 Facade 와 멀티모듈 기반의 컴포넌트 구조가 더
적합하다고 생각하게 되었습니다. 중요한 업무 흐름은 Facade 에 두어 개발자가 통제하고, 나머지 컴포넌트는 테스트와 명확한 입력/출력 계약으로 검증할 수 있었습니다.

## 문서화와 설계 선행

AI에게 많은 구현을 맡기려면 역설적이게도 설계에 더 많은 시간을 써야 한다고 생각합니다.  
통제 영역의 분리를 위해서는 기본적인 레이어 설계가 필요했고, 자연스럽게 관심사가 분리 되었습니다.   
새로운 업무 요건도 분리된 관심사의 일부이기에, 생각의 범위가 작아지고 업무 내용, 의사 결정의 문서화가 쉬워져 동료와의 업무 공유도 쉬워졌습니다.

```text
opengateway-data-plane-backend/       # OpenAI 호환 Gateway, Provider 라우팅, 모델 서빙
opengateway-control-plane-frontend/   # Admin, 로그, 사용량, API Key 관리 화면
opengateway-control-plane-backend/    # 계정, 과금, 사용량 기록, 내부 Admin API

opengateway-claude-skills/            # 레포별 정책, 리서치, AI 작업 기준
├── CLAUDE.md
├── AGENTS.md
├── .claude/skills/
├── .agents/skills/
├── opengateway-core/                 # 공통 정책, 아키텍처, 과금, 인증
├── opengateway-research/             # 진행 중인 리서치
├── opengateway-research-legacy/
├── opengateway-cp-be/                # Control Plane Backend 정책
├── opengateway-cp-fe/                # Frontend 정책
├── opengateway-dp-be/                # Data Plane Backend 정책
```

[OpenGateway](./03_opengateway.md) 개발은 이 방식을 가장 잘 적용한 사례입니다.

- 1명의 주니어 개발자와 함께 DP, CP-BE/FE 를 동시에 기획/개발하면서도, 여러 레포와 개발자 사이에서 정책과 스타일을 일관되게 유지해야 했습니다.
- 유관 작업자가 매번 모여 협의하거나, 과거 맥락을 기억이나 Linear 에서 다시 꺼내는 방식만으로는 AI를 제대로 활용하기 어렵다고 보았습니다.
    - 그래서 정책과 작업 기준을 Claude Skill 형태로 관리하고, 이를 프로젝트의 single source of truth 로 두는 방식을 선택했습니다.
    - Skill 은 기본적으로 Markdown 이기 때문에 AI 친화적이고, 사람도 읽기 쉬우며, CLI 와의 호환도 좋았습니다.
- 문서를 작성할 때도 AI와 긴 대화를 이어가면 컨텍스트가 오염되고 논점도 흐려지기 쉽기 때문에 handover 개념을 도입했습니다.
    - Provider 정책, 모델 라우팅, 과금, 프론트 기능 기준 같은 복잡한 주제는 테크 스펙 형태의 리서치 문서로 먼저 정리했습니다.
    - 이렇게 AI와 먼저 논의된 리서치 문서를 동료 개발자와 리뷰한 뒤, 합의된 내용만 각 서비스, 또는 공통의 정식 정책으로 승격시켜 관리 했습니다.
- 이런 방식 덕분에 개발자의 변경이나, 지속적인 개발 속에서도 일관적인 맥락과 정책을 유지할 수 있었습니다.

## 도구보다 중요한 것

agentic coding, harness engineering, Hermes 같은 hype 한 단어들이 많이 나오지만, 이것들을 모두 따라가야만 한다고 생각하지는 않습니다.

- Harness engineering 도 말은 거창하지만, 본질은 AI를 잘 다루기 위한 업무 흐름을 설계하는 개념에 가깝습니다.
- 빠르게 주목받았던 OpenClaw 도 순식간에 Hermes 로 관심이 옮겨가는 것처럼, AI 개발 도구의 최전선을 계속 따라가는 것은 상당히 어렵습니다.
- 새로운 도구가 당장은 효율적일 수 있지만, 동시에 학습 비용과 불안정성을 가져오기에 실무를 하면서 이것을 어디까지 수용할지 항상 고민하게 됩니다.
- 그래서 저는 계속해서 좋은 도구를 찾는 것 보다는, 일정 수준 안정화된 도구를 중심으로 제 업무에 특화된 하네스와 운영 노하우를 쌓는 방식을 선택 했습니다.

결국 도구보다 중요한 것은 CS 와 같은 기본 지식, 경험에서 나오는 직관, 코드 스멜을 감지하는 능력이라고 생각합니다.

- 과거에는 중요했던 언어와 프레임워크의 코딩 능력은 상당 부분 AI로 넘어가고 있고, 저 역시 과거에는 쉽게 접근하기 힘들었던 파이썬과 프론트엔드 개발을 실무 레벨로 병행하고 있습니다.
- 특정 기술의 높은 숙련도보다, 문제를 해결하기 위한 키워드와 개념을 뽑아내고 AI와 함께 결론을 도출하는 능력이 더 중요해지고 있습니다.

또한 AI는 모듈화, 추상화, 테스트 가능성, 상태 관리, 장애 격리 같은 기술적인 주제에 대해 그럴듯한 답을 잘 만들어냅니다.  
불필요한 wrapper 로직을 만들어 복잡도를 높이기도 하고, 너무 원칙에 가까운 대답을 하기도 합니다.
그렇기에 AI의 제안을 비판적으로 수용해서 현재 시스템과 운영 맥락에 맞는지를 판단하는 것은 여전히 개발자의 역할입니다.

## 적극적인 실험과 학습

하지만 앞에서의 언급처럼 AI를 항상 보수적으로만 사용하고 있지는 않습니다.  
양쪽을 모두 알아야 더 잘 사용할 수 있다고 생각하기 때문에, 영향 범위가 제한된 사이드 프로젝트나 마이너 개발건에서는 AI에 더 의존적인 방식도 적극적으로
실험하고 있습니다.

프론트엔드와 파이썬 개발이 그러했고, `코드를 보지 않고 머지합니다` 의 철학으로 만든 사이드 프로젝트 [read4ai](https://github.com/read4ai/read4ai-excel) 가 그러합니다.

- Excel 문서를 AI가 읽기 좋은 구조로 변환하고, 그 결과가 AI 친화적인지 benchmark 와 judge 흐름으로 검증하는 오픈소스 프로젝트 입니다.
- 이 프로젝트에서는 기대 결과와 평가 기준을 먼저 정의하고, AI에게 구현을 위임한 뒤, 반복 가능한 검증 흐름으로 품질을 끌어올리는 데 초점을 두었습니다.
- 단순히 코드를 생성하는 것이 아니라, 입력 데이터, 기대 결과, 평가 기준, 실패 사례를 먼저 정리해 AI가 반복적으로 개선할 수 있는 환경을 만드는 방식입니다.

LinkedIn, GeekNews, Medium, release note 등을 통해 꾸준히 AI 정보를 습득하고 팀에도 공유하고 있습니다.  
그리고 AI에서 가장 좋은 학습법은 직접 써보는 것이라고 생각합니다. Claude Code 의 버전 히스토리를 참고하고, LLM API를 직접 호출해보면서 제 업무 흐름에 적용 가능한 방식인지 지속적으로 학습하고
있습니다.
